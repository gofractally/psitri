05 Both engines

Practically
lock-free.

Parallel readers traverse stable snapshots without node mutexes while the writer builds the next version. Atomic coordination keeps the read path independent of the writer’s tree work.

Root acquisition and publication synchronize. Active reads do not wait for the writer; residency pins defer storage reuse.
06 Native architecture

Independent roots.
Independent work.

The underlying storage layer supports writers on independent root tables. It is the foundation for parallel work on disjoint state.

Native SAL supports a writer per root. The shared engine API requires one serialized writer.

02 / Choose your operating envelope

Choose your engine.
Keep your API.

Two maintained profiles. One source interface. Choose for your working set, then measure with your actual data.

RAMResident data

Small Engine

psitri::small_engine

A direct-address adaptive radix tree for databases and retained versions that fit in RAM. Skip the movable-object control-block lookup.

  • Fixed addresses and reference-counted snapshots
  • Competes with specialist in-memory ART libraries
  • Large values and range reads through the shared API
Capacity, precisely.

The Small Engine defaults to a 32 GiB ordinary arena and can address just under 512 GiB with five-byte handles. Nodes, metadata, and retained versions consume capacity. Large values use a separate arena; size your working set to fit available RAM.

DISKGrowth beyond RAM

Large Engine

psitri::big_engine

Movable, reference-counted storage for databases expected to outgrow memory. Designed to keep an active working set while the full database lives on disk.

  • Segment compaction and optional hot-object promotion
  • Owned subtrees, retained revisions, and native savepoints
  • Segment-aware large values with range reads
Storage that can grow with your application.

The Large Engine is the default engine for disk-backed storage. Use compaction and hot-object promotion to manage locality as your dataset grows, with snapshots and the same core API as the Small Engine. See the operating guide for durability and validation status.

A familiar
way in.

The MDBX C/C++ compatibility implementation is included. SQLite, RocksDB, LevelDB, and DuckDB have separate integration implementations; versions targeting this repository’s shared engine API are not available. The separate integration suite includes bank benchmarks for RocksDB and SQLite, and a TATP benchmark for DuckDB.

Compatibility has a performance cost. Another API imposes its own transaction, cursor, and ownership workflow. Translating that workflow adds overhead and can limit optimization paths available through psitri’s native interface.

Use a compatible API to reduce migration work. Use the native API for direct access to owned snapshots, composable trees, and engine-specific capabilities. Benchmark the interface your application will actually use.

C++23 / inside your application function

Before you build

Good questions.
Direct answers.

Is psitri ready for production?

The Small Engine and Large Engine implement the public C++ API and pass its behavioral tests, including snapshots, rollback, range reads, and clean durable reopen. Comprehensive crash/power-loss and sustained beyond-RAM validation is incomplete. Evaluate those requirements against your workload before production deployment. GC and tiered configurations are explicitly experimental.

Read the operating contract ↗
Are snapshots really instant?

Keeping a snapshot retains an existing tree root; it does not copy the database. Later writes copy the affected paths. Retaining many changing versions costs storage, and eventually releasing a large unreachable tree can involve substantial reclamation work. In-memory snapshot ownership alone is not a persistent backup.

Is this faster than MDBX or RocksDB?

The published native bank workload shows higher throughput than MDBX, along with a higher disk high-water mark. Separate RocksDB and SQLite integration bank results are also available; their configurations and correctness status are documented in the evidence guide. Results depend on the tested engine, interface, workload, and durability settings. Measure your own workload and include storage, memory, latency, and recovery requirements in the comparison.

Explore the integration benchmarks ↗
Can I switch engines without migrating data?

You can target the same source-level concept and choose an engine at compile time. Physical formats differ. Switching backend types or replacing another database requires a deliberate data migration; changing a C++ alias does not convert files.

What does “practically lock-free” mean?

The read path avoids node mutexes, allowing readers to traverse snapshots in parallel with the writer’s tree work. The Large Engine uses atomic residency markers so readers can continue while objects are relocated; the Small Engine reads fixed addresses protected by its snapshot. Acquiring or publishing roots can synchronize, and allocation, storage I/O, and maintenance have their own coordination. This is a mutex-free read path, not a formal lock-free guarantee for every database operation.

See the synchronization boundaries ↗
Can multiple threads write at once?

The underlying SAL architecture supports independent root writers. The maintained portable database API currently requires a single serialized writer, with separate reader sessions on their own threads. The MDBX shim also preserves MDBX’s one-writer semantics. Use separate reader sessions to keep reads independent of the writer’s tree updates.

How do I evaluate it for my application?

Start with the shared API guide or the compatibility-layer status. Pin revisions, exercise the calls you use, select durability explicitly, and run the same workload with realistic data sizes and snapshot lifetimes. Save results with the benchmark recorder, including failures. Repeated matched runs are more useful than one headline number.
